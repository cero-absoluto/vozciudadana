## What was fixed and how

### Vulnerability #3 — `target_validation` (HIGH)
The backend now calls Wikidata directly using `target_wikidata_id` and computes
`target_validation` server-side via `verifyTargetBackend()`. The check traverses the
Wikidata subclass hierarchy (`P31`/`P279*`) against a small set of public-authority classes
rather than a flat identifier whitelist; an allowed public classification takes precedence over
a rejected one, so public enterprises are admitted while private companies and political parties
are rejected, and verdicts are cached. The client-supplied value is ignored. If Wikidata is unavailable, falls back to `NEEDS_REVIEW`,
never to `ALLOWED`. Only the entity ID is sent to Wikidata — no user data.

### Vulnerability #1 — Verb matching (HIGH)
- Added conjugations in first person plural ("pedimos", "solicitamos", "proponemos")
- Changed from `String.includes()` to word-boundary regex (`\b`)
- Removed `public` from `REQUIRED_VERB_ROOTS` (collided with "público", "publicidad")
- Scan now covers `title + description + demands`, not only `demands`

### Vulnerability #4 — Domain blocking (MEDIUM)
- Switched from exact-match Set to registrable domain (eTLD+1) extraction
- Added `chng.it`, `openpetition.eu/de`, `mesopinions.com`
- Trailing dot (FQDN notation) now normalised before comparison

## Remaining limitation (accepted, by design)

`tipo_abuso` can be semantically bypassed by selecting `other_public_abuse`
or `opacity` for any content. This is an accepted limitation: Voice Protest
does not verify truth, and cannot judge whether a declared abuse type is
accurate. The platform relies on the other three rules to maintain its identity.

> Note (July 2026): the closed list of accepted abuse types was broadened from seven to sixteen, grounded in the UNCAC, European Ombudsman and EU Charter frameworks. This widens the range of legitimate public grievances the platform can express, but does not change the limitation above — the declared `tipo_abuso` still cannot be verified for accuracy.

## RLS Fix — Supabase Row Level Security

**Date:** June 2026  
**Identified by:** Opus 4.8 audit (PostgREST/anon key vector)  
**Fixed by:** SQL migration in Supabase panel

### Problem

The `protests_service_write` policy had `roles: public`, meaning anyone with
the Supabase anon key could INSERT/UPDATE/DELETE directly into `protests` via
PostgREST, bypassing all four backend admission rules entirely.

This was the most fundamental bypass: no verb check, no domain check, no
Wikidata validation — a direct database insert.

### Fix applied

```sql
drop policy if exists protests_service_write on protests;

create policy protests_service_write
  on protests for all to service_role
  using (true) with check (true);
```

### Result verified

| policyname             | cmd    | roles          |
|------------------------|--------|----------------|
| protests_public_read   | SELECT | {public}       |
| protests_service_write | ALL    | {service_role} |

- `protests_public_read` — anyone can read (protests are public). Correct.
- `protests_service_write` — only the Railway backend (service_role) can write. Correct.

The PostgREST/anon key vector is now closed. All writes to `protests` must
go through the backend admission rules.

### Migration file

`supabase/migrations/20260620_fix_protests_rls_service_role.sql`

## Update — 21 June 2026

### Local scope GPS classification (design note, not a vulnerability)

The new `local` scope (city/municipality) uses GPS coordinates to classify adhesions into three tiers in the public report: GPS confirmed within the declared municipality, national participants without local GPS, and international participants.

**GPS is not used as an exclusion filter.** A participant without GPS, or with GPS outside the municipality, is not rejected — they are classified transparently in the report. This is a deliberate design decision consistent with the platform's core principle: Voice Protest verifies participation, not legitimacy.

The GPS spoofing threat (§14.3 in the Audit Alignment Framework) applies here: a participant could spoof GPS coordinates to appear locally verified. The accepted response is unchanged — GPS contributes to classification and reliability scoring, not to eligibility. A spoofed GPS gains a participant a stronger local classification in the report but does not grant additional rights.

### Municipality identification via OSM ID (design note)

The declared municipality is stored as an OSM relation ID (admin_level=8), not as a text string. This eliminates name ambiguity across languages (San Sebastián/Donostia, Ourense/Orense, etc.) and is validated for all 27 EU member states. The OSM ID is compared server-side against the reverse-geocoded OSM ID from the participant's GPS coordinates.

## Update — 28 June 2026

### RLS enabled on all remaining tables

The `protests` fix above (20260620) closed the PostgREST/anon-key vector for the `protests` table. A follow-up review confirmed — by live query against `pg_tables` — that Row Level Security was still **disabled** on every other table in the `public` schema. Although the frontend holds no Supabase client and all data flows through the Railway backend (service-role key, which bypasses RLS), the anon key plus PostgREST remained an attack surface independent of the frontend.

RLS was therefore enabled, each with a service-role-only policy, on the 14 remaining tables:

`groups`, `group_members`, `vouches`, `vouch_requests`, `invite_links`, `institutional_members`, `email_otp_requests`, `email_otp_rate_limit`, `platform_fund`, `financial_movements`, `kofi_protest_map`, `integrity_records`, `source_validations`, `admin_log`.

**Result verified:** a repeat of `select tablename, rowsecurity from pg_tables where schemaname = 'public' and rowsecurity = false` now returns **no rows** — RLS is active on every table.

**Migration file:** `supabase/migrations/20260628_enable_rls_remaining_tables.sql` (idempotent — drop-if-exists policies, safe to re-run).

### Related privacy changes (same review)

Two data-retention changes were applied in the same session and are documented in full in the canonical privacy document and the Audit Trail:

- **Irreversible anonymisation of adhesions at 90 days** replaces the previous soft-delete. Individual/linkable fields are permanently set to null; the aggregate row is kept so the closed public report stays intact. Migration: `20260628_anonymize_old_adhesions.sql`.
- **Verified-device retention (270 days of inactivity).** The `devices` table (device id to phone-number hash) now carries a `last_seen` column refreshed on each adhesion; a daily job deletes any device inactive for 270 days with no referencing adhesion. Migration: `20260628_device_retention_270d.sql`.

## Update — 12 July 2026

### Public-report classification integrity (correctness fixes, not vulnerabilities)

An end-to-end testing session against a live regional convocatoria surfaced a set of
defects in the territorial classification pipeline of the public report. None of them
opened an attack surface, but all of them affected the correctness of the published
artifact — which for this platform is an integrity matter. Full detail per fix is in
the Audit Trail (Session corrections — 12 July 2026); the security-relevant summary:

- **Country classification by localized name → ISO code.** The national/international
  grouping compared localized country names from mixed-language providers
  ("Spain" vs "España"), misclassifying domestic no-GPS adhesions as international.
  Fixed with a new `adhesions.pais_code` column (ISO 3166-1 alpha-2, format-checked)
  captured at verification time. Migration `20260712_adhesions_pais_code.sql`; the new
  column is covered by the existing service-role-only RLS policy on `adhesions`.
- **Regional reinforcement chain unreachable.** Three independent 'local-only'
  conditions (reinforce button visibility, reverse-geocode zoom level, and the
  issuance of the single-use GPS update token itself) made post-adhesion GPS
  reinforcement silently impossible on regional convocatorias. All three fixed;
  the lesson — every condition on a shared local/regional path is a silent failure
  point — is recorded in the Audit Trail.
- **Phantom-token hardening.** The insert into `gps_update_tokens` did not check its
  error result: on failure the backend still returned the generated token to the
  client, producing undiagnosable 404s on the later PATCH. The insert is now
  error-checked (no token is issued if persistence fails) and the full reinforcement
  path is instrumented with structured logs (issuance, zoom level, derived OSM id,
  completion) for auditability.
- **Honest client feedback.** The reinforcement UI previously gave implicit visual
  confirmation when the browser granted the GPS permission, regardless of whether the
  server accepted the update. Confirmation is now shown only on a successful server
  response; failures surface an explicit error.

**Attack surface:** unchanged. No new endpoints, no new client-side keys, RLS posture
unchanged (service-role-only writes). The GPS interstitial added at the joining step is
a client-side prompt; location remains optional and non-gating, consistent with the
design note of 21 June 2026.

## Update — 16 July 2026 (continued session)

### Two new hard admission rules — source must be real and must be a documentary source, not a platform post

A UX review of the source-quality indicator (previously informational only, computed by `routes/source.js` and shown during drafting but never enforced) found that the actual admission gate in `routes/protests.js` checked only one thing about `fuente_url`: whether its domain was a known petition platform. Nothing stopped a social-media post from being submitted as a source, and nothing stopped a URL that was live but entirely disconnected from the reported event. Both gaps are now closed with two new hard rules, alongside a refactor that puts every fetch/classification primitive shared between the preview and the real gate in one module (`apps/api/src/lib/sourceCheck.js`), so the two paths cannot silently diverge as they previously had for verb checking (see Vulnerability #1 history above, and the corresponding frontend fix logged in the Audit Trail, 16 July 2026).

**Rule 1a — Social media and user-generated-content platforms rejected as sources.** Same mechanism as the existing petition-platform block (registrable-domain match against a Set), applied to a second, distinct list: Facebook, Instagram, TikTok, Twitter/X, YouTube, Reddit, WhatsApp, Telegram, Medium, Substack, Blogspot, WordPress.com. Rationale: a social media post is not a documentary source under any interpretation — it can be edited or deleted by its author, was not subject to any editorial process, and proves nothing about the reported event beyond that someone once typed something. This is a distinct concept from the petition-platform block and is enforced as a separate rule for that reason, not merged into it.

**Rule 1b — Minimal connection between source and event required.** The backend now fetches the submitted URL and checks that the recipient's name, or at least two distinct words (>4 characters) from the title and demands, appear on the fetched page. This is deliberately **not** a quality bar — a source from an unrecognised or foreign-language outlet, or one that scores poorly on the informational documentary-quality indicator, still passes. The rule exists only to reject a source with **no detectable connection at all** to the event. Per the founder's explicit instruction: platform admission rules must never block on reputation or documentary strength, only on the presence of a real, checkable link between the source and the claim. If the URL cannot be fetched at all (timeout, DNS failure, 404, 5xx), the event is also rejected. A paywalled response (401/403/429) that still exposes readable metadata is not treated as a failure, since many legitimate news sources sit behind a paywall.

### Correctness fix — informational score, not a vulnerability

`source.js`'s `wikidata_verified` flag, sent by the frontend as part of the informational documentary-quality score, read a form field (`focal_point_wikidata_id`) that did not exist — the real field is `target_wikidata_id`. The flag was therefore always `false`, silently capping the informational score for every event. Fixed by correcting the field name read on the frontend. This affects only the informational indicator shown while drafting — it never touched the real, independently-computed Wikidata admission check described under Vulnerability #3 above.

**Attack surface:** the two new rules are additive hardening of the existing admission boundary — no new endpoint, no new client-supplied trust. `evaluateSource()` in the new shared module performs the fetch and classification server-side exactly once per request; the frontend cannot supply or override its result.

## Update — 18 July 2026

### New attack surface — `reports.voiceprotest.org`

A second custom domain, `reports.voiceprotest.org`, now points at the same Railway service as `api.voiceprotest.org` (Discoverability Phase 2 — see the master design document and Audit Trail for the product rationale). It serves a public, read-only HTML rendering of any convocatoria/report by id, generated fresh from Supabase on every request, plus a dynamic `sitemap.xml`. All routes live in `apps/api/src/routes/reports.js` and are gated on the `Host` header, so `api.voiceprotest.org` is unaffected.

This is a genuinely new, unauthenticated public surface, and an internal review (18 July 2026, structured against a public-trust/privacy/transparency/security/simplicity/sustainability rubric) found three real hardening gaps, all now fixed:

- **No route-specific rate limit on the most expensive query.** The app-wide limit (120 req/min, `server.js`, already in place before this review — an earlier informal review had overstated this as entirely absent, corrected here) covers `reports.js` too, but `/sitemap.xml` runs an unauthenticated query of up to 5,000 rows and could, on its own, consume that shared budget at the expense of legitimate API traffic. Fixed with a stricter, route-scoped limit (20 req/min) via `@fastify/rate-limit`'s per-route `config.rateLimit` option.
- **No caching — every hit re-queried Supabase.** Fine at current traffic; a real cost-amplification vector once a report link is shared widely or a crawler revisits aggressively. Fixed with a bounded, 30-second in-memory cache per convocatoria id (capped at 2,000 entries, oldest evicted first, so an enumeration attempt can't grow it unboundedly). This cache is read-only presentation; the actual adhesion/verification flow never reads it.
- **`fuente_url` rendered as a clickable link with no scheme check.** The existing admission rules (Rule 1a/1b above) mean a non-http(s) value shouldn't reach this field today, but the render path had no defence of its own beyond HTML-escaping, which prevents broken markup but not a `javascript:` scheme from being clickable if one ever got in some other way. Fixed with `safeHref()`: only `http:`/`https:` URLs are rendered as an `<a href>`; anything else is shown as plain, non-clickable text.

**Attack surface, net:** one new unauthenticated read-only endpoint family, no new secrets, no write path, no change to the admission rules or verification signals — those remain exclusively in `routes/protests.js`. `reports.js` only ever reads already-public convocatoria data.

## Update — 23 July 2026 — External audit (independent reviewer)

An independent external auditor reviewed the codebase and reported seven findings (VP-SEC-001 through VP-SEC-007), all confirmed against the actual code before any fix was applied. All seven are now resolved. An eighth (VP-SEC-008) was identified while implementing the fix for the first three and is recorded here as open, not yet fixed — see below.

### VP-SEC-001 — Join endpoint did not verify phone_hash belonged to device_id (High, confirmed)

`POST /:id/join` accepted `phone_hash` and `device_id` directly from the client body and trusted them outright — nothing checked that this `device_id` had ever completed OTP verification for this exact `phone_hash`. A code comment in this file had previously asserted that reaching the insert "requires having completed real OTP verification for the exact phone number" (Audit Trail, 21-22 July 2026) — that assertion was never actually enforced.

The auditor proposed a minimal fix (query `devices` for `id = device_id AND phone_hash = phone_hash AND verified_at IS NOT NULL` before trusting the value) and a more robust architecture (a short-lived signed token issued at verification, carrying the identity, so the client never sends `phone_hash` at all). Both were sound; the robust version was implemented, since it also resolves VP-SEC-002 and VP-SEC-003 below rather than needing a separate fix for each.

**Fix:** new module `lib/participationToken.js`. `POST /verify-otp` and the new `POST /device/:id/reauth` (see VP-SEC-002) issue a signed, HMAC-verified `participation_token` (30-minute expiry, purpose-scoped to `join_protest`). `POST /:id/join` now requires this token instead of raw `phone_hash`/`device_id`; both are read from the token's verified payload, never from client-asserted fields.

### VP-SEC-002 — device_id acted as a permanent, unauthenticated bearer credential (High, confirmed)

`GET /device/:id` returned a device's `phone_hash` and `country_code` in clear to anyone who supplied its `device_id` — no session, no signed token, no proof of recent OTP possession. `GET /device/:id/locks` similarly revealed which convocatorias a device had joined. Since IDs are not necessarily unguessable and can leak via browser storage, logs, a malicious extension, a future XSS, or a shared device, a bare device_id functioned as a permanent bearer credential with no second factor — and the previously fully-open CORS policy (VP-SEC-006) would have let any origin read the response if it obtained the ID.

The auditor's proposed structural fix — keep two client-side values, a public `device_id` and a secret `device_secret`, with only `HMAC(device_secret)` stored server-side — was implemented as specified.

**Fix:** new `devices.device_secret_hash` column (migration `20260723_device_secret_hash.sql`). `device_secret` is generated once, at a device's first verification, returned to the client exactly that one time, and never again. `GET /device/:id` is removed; `POST /device/:id/reauth` and `POST /device/:id/locks` now require the secret and return a fresh `participation_token` (never raw `phone_hash`) on success.

### VP-SEC-003 — OTP verification amounted to an unbounded, effectively 270-day authorization (High, confirmed as design)

Because `device_id` alone unlocked `phone_hash` retrieval (VP-SEC-002), a single OTP verification effectively authorized joining any future convocatoria for as long as the device record existed (270 days, its retention window) — with no separate expiry, rotation, or revocation for the *authorization* itself, as distinct from the *device registration*.

The auditor recommended separating three concepts: device registration (270 days), an authenticated session, and a short authorization to join. Implemented with two of the three (registration, and a short join-authorization token) rather than a full session layer, since the device-secret reauth path already bounds re-authentication to a deliberate, provable action rather than passive possession of an ID.

**Fix:** `participation_token` expires in 30 minutes regardless of how long the underlying device registration persists. A returning device must present its `device_secret` to obtain a fresh token every time it wants to join something — device registration validity and join-authorization validity are no longer the same thing.

### VP-SEC-004 — "GPS confirmed" accepted unvalidated client-supplied coordinates (Medium-High for public trust, confirmed)

`gps_confirmed` was computed as `gps_lat != null && gps_lng != null` — no bounds check at all. A value like `{lat: 999}` was accepted as "confirmed" and could raise an adhesion's reliability score to 92-95%.

**Fix:** coordinates are validated (`-90≤lat≤90`, `-180≤lng≤180`, `0<accuracy≤50,000m`) before being treated as present; out-of-range values are treated as absent (same reduced-reliability path as no GPS at all), in both `POST /:id/join` and the GPS-reinforcement endpoint `PATCH /:id/adhesion` (a second occurrence of the same gap, found while fixing the first, not originally flagged by the auditor).

**Not yet done — flagged by the auditor, deferred by mutual agreement:** renaming `gps_confirmed` to something like `gps_signal_provided` for terminological honesty (it is a signal, not proof of presence). This touches the database column, the informe rendering, and existing documentation that already uses "GPS confirmed" as a defined term (Methodology, §4.1) — deferred pending an explicit decision, not forgotten.

### VP-SEC-005 — SSRF risk in source-URL validation (High, confirmed)

`safeFetch()` (`lib/sourceCheck.js`) used `redirect: 'follow'` with no validation of the IP a hostname resolves to. A hostname-string blocklist existed (`PRIVATE_HOSTNAMES` in `routes/source.js`) but ran once, before the fetch, in a different file — and the real admission-gate path (`protests.js` → `evaluateSource()` → `safeFetch()`, used at convocatoria creation) never went through it at all. Even where the check did run, a redirect to an internal address would be followed blindly.

**Fix:** `safeFetch()` rewritten to resolve DNS and reject private/reserved IPv4 and IPv6 ranges (including link-local/cloud-metadata addresses) before connecting; `redirect: 'manual'` with up to 3 manually-followed hops, each re-validated the same way. `PRIVATE_HOSTNAMES` in `source.js` is kept as a cheap early filter but documented as non-authoritative — the real protection is now in one place, used by every caller.

### VP-SEC-006 — CORS accepted any origin for the entire API (Medium, confirmed)

`origin: (origin, cb) => cb(null, true)` applied globally, though the comment claimed it was for the embeddable widget only. Checked: only one endpoint, `GET /:id/informe`, is actually fetched from third-party origins (by `widget.js`). Combined with VP-SEC-002, open CORS meant any origin could read a device's data once it had the ID.

**Fix:** restrictive origin allowlist by default (`voiceprotest.org`, `www.voiceprotest.org`); `GET /:id/informe` opts back into any-origin access explicitly, at the route level.

### VP-SEC-007 — reCAPTCHA failed open if its secret was unset (Medium-High, confirmed)

Two separate, drifted implementations existed — `routes/protests.js` and `routes/users.js` — both with `if (!secret) return;`, silently skipping verification entirely on a missing `RECAPTCHA_SECRET` rather than rejecting.

**Fix:** unified into `lib/recaptcha.js`, the only implementation now. Fails closed in production (added to the startup fail-fast check alongside `PHONE_HASH_SECRET`/`NULLIFIER_SECRET`); still permissive in development so local work isn't blocked. Also added the hostname check the auditor recommended — Google's siteverify response includes the hostname a token was generated on, checked against an expected-hostnames list to reject a token replayed from a different site.

### VP-SEC-008 — Institutional (email-domain) adhesion path bypasses all of the above entirely (High, confirmed — OPEN, not yet fixed)

`routes/institucional.js`'s `verify-otp` performs its own direct `INSERT INTO adhesions`, computing its own nullifier, with no `participation_token`, no `device_secret`, and — found while confirming this finding, not originally flagged — **no reCAPTCHA at all** on either of its endpoints, **no IP-based rate limit** (the SMS path caps at 10/hour/IP; this path has none), and **the OTP code is stored in plaintext** in `email_otp_requests` (the SMS path never sees its own OTP code — Twilio Verify manages it externally). This path is not vulnerable to the exact VP-SEC-001 attack (its identity hash is computed server-side, inside the same request that validates the real OTP code — there is no separate step where a client-asserted identity is trusted), but it is a second, independently-maintained way to create an adhesion, already measurably less protected than the first.

The auditor's recommendation — consolidate all adhesion creation (SMS, institutional, and any future method) behind a single `AdhesionService`, so a fix or a new control is written once, not per-path — is agreed and scheduled as the first item of the next security pass, not folded into this one, given its scope.
