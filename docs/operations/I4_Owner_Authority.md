# I4 synthetic Owner authority integration

Owner Gate: Project Owner “autorizo”, 2026-10-04 20:31 Europe/Madrid. A3 temporary only for isolated code, additive migration, tests, documentation and existing validation branch/CI. This is not real Owner authentication or a production activation.

`ownerAuthority.js` composes an independently trusted synthetic identity adapter and a dedicated nonprivileged review pool. It does not mount routes on the production server. No client chooses the old authenticator. A private random credential bridges existing review service inside the same transaction; it is never returned to callers. The adapter must verify issuer/audience/stable subject/session expiry/authority epoch and operation-specific confirmation. Editable claims and donor/PSP tokens cannot confer authority.

The fixture adapter uses opaque server-held handles, not a real IdP, cryptographic login implementation or real step-up verification. `stepUp` is a trusted fixture assertion; operation confirmation independently binds digest, challenge, principal and epoch. Adoption of an actual IdP, enrollment and credentials needs current documentation, a separate gate and real evidence. No supplier selected.

Private principal state, one-use challenges, immutable decision bindings, individual session revocations and recovery audit use separate enrollment authority. Enrollment has neither reviewer nor finance membership. Review cannot enroll/recover; finance cannot write authority. Issuance and challenge consumption share one transaction and preserve old simulated provenance, adding explicit synthetic identity binding. Exact retries preserve the prior decision; changed request conflicts. Challenge TTL is explicitly two minutes TEST ONLY; identity fixture expiry ten minutes TEST ONLY, not policy for production.

Every identity action checks current authority. Principal suspension increments epoch under the same advisory transaction lock used by financial reservation/allocation triggers. Application rechecks both authority epoch and existing financial conditions. A revocation committed first blocks subsequent use; use committed first remains an attributable historical reservation. Later allocation still rechecks authority and rolls back if stale. Existing facts are never retrospectively undone.

After explicit synthetic principal enrollment, new issue/revoke commits need bindings; no fallback to old weak review authenticator can commit new decisions. Legacy fixture decisions remain preserved and unbound; once enrollment exists they cannot be newly applied without a binding. A DB owner can bypass these fixture controls; restricted review SQL remains a trusted issuer within its grants, not a guarantee against a compromised issuer. Enrollment may directly mutate its own domain; recovery function provides audited idempotent suspend/reenroll, and the role is a trusted fixture custodian. It is not a product recovery backdoor.

Individual session revocation blocks new identity actions; it does not revoke previously issued financial decisions. Revoke a decision or suspend principal to prevent its future financial use. Recovery increments epoch, requires a suspended principal before reenrollment and never restores old decisions. Audit contains opaque IDs/evidence, no donor phone/HMAC/raw IdP payload.

Native PostgreSQL tests report separate restricted roles, twenty approval replays, twenty recovery replays and both observed lock orders between suspension and financial use. PGlite regressions test rejected claims/changed bindings, expired/consumed challenge, rollback, revocation, recovery and role boundaries. PGlite serializes transactions and does not substitute for native race verification.
