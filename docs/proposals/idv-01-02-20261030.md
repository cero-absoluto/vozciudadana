# IDV-01 e IDV-02 — candidato acotado

Fecha: 30/10/2026. Base: `ab81e21de39edd1c91f2d2084398469d3f0c04b2`.
Estado: aplicado y publicado con autorización del Owner el 30/10/2026. Evidencia final: `docs/idv-01-02-publication-20261030.md`.

Lo que sigue conserva la descripción y validación del candidato previo a publicar.

## IDV-01: correo obligatorio en convocatorias institucionales

- La solicitud SMS con convocatoria institucional se rechaza antes de reservar cuota o enviar el SMS. No consulta si ese teléfono ha participado.
- La adhesión con credencial de teléfono se rechaza en el servicio común, aunque no se requiera censo. El cliente muestra una indicación fija, traducida en los cuatro idiomas, para volver y usar la vía de correo.
- La propuesta SQL exige `institutional_email_otp` para nuevas adhesiones cuando existe dominio institucional y cubre cambios posteriores de identidad hacia métodos distintos. Conserva los avales y la excepción de fundador ya aprobados.
- No acredita vínculo oficial entre dominio e institución, identidad civil, rol o condición actual de alumno: esos trabajos siguen abiertos.

## IDV-02: GPS excluido en riesgo alto/crítico

- Auth consulta el riesgo de la convocatoria actual, no un valor antiguo de sesión. No pide ubicación para riesgo alto/crítico o dominio institucional.
- Verify no incluye GPS guardado en la adhesión de esos casos, no ofrece refuerzo y vuelve a comprobar la convocatoria antes de solicitar ubicación para reforzar.
- La API descarta las coordenadas de creación antes de geocodificarlas; no emite nuevos tokens GPS y rechaza tokens anteriores en el refuerzo. La estimación IP vigente permanece: no equivale a GPS.
- La propuesta SQL impide añadir GPS confirmado, identificador OSM, señal GPS o coordenadas crudas en los catálogos que aún conservan esas columnas. También controla nuevas señales en UPDATE y cambios de contexto territorial. Permite retirar datos históricos para anonimización sin reescribirlos por esta publicación.
- El trigger conserva la serialización exclusiva de admisión/censo. Los cambios únicamente geográficos usan SHARE, compatible con el refuerzo atómico, para evitar una escalada de bloqueo entre dos adhesiones.
- Un cliente modificado aún puede transmitir coordenadas al servidor; no se promete impedir su recepción por HTTP. La aplicación las excluye del procesamiento geográfico/persistencia de esta ruta. La política no borra ni reinterpreta adhesiones históricas.

La comprobación actual en Supabase se limitó a metadatos: MD5 de función
`571ff4505a3571d89cbc58e06efe35d8`, trigger esperado, SECURITY INVOKER y
EXECUTE restringido a propietario/service_role coinciden. Las tres columnas GPS
heredadas existen y quedan cubiertas por la propuesta. No se consultaron filas
de adhesiones.

No son pruebas de OTP/proveedores reales ni ensayos en Chromium. Los permisos y tablas de la base sintética no sustituyen la verificación del catálogo/RLS real. No se han leído datos personales ni secretos ni escrito en producción.

## Publicación y límites

Los cambios de API/web y SQL deben revisarse juntos. SQL de aplicación:
`docs/proposals/idv-01-02-admission.sql`; reversión:
`docs/proposals/idv-01-02-admission-rollback.sql`. Ambos abortan ante cambios inesperados de la función de referencia; aplicación comprueba además el trigger. CREATE OR REPLACE mantiene propietario y ACL. No se añaden SECURITY DEFINER, funciones nuevas, roles o permisos.

Antes de publicar: comprobar en solo lectura que el catálogo real coincide, revisar el diff final, autorizar la aplicación SQL y la publicación API/web, verificar después las restricciones y salud sin OTP real. Una denegación por cambio concurrente de política revierte la transacción; la API devuelve un error controlado.

Este candidato se separa de la preparación más amplia guardada en la rama
`fix/identity-verification-20261030` (commit `8e61667a`). IDV-03–12, puntuación,
territorio, vigencia del censo y prueba OTP real conservan sus pendientes. No se
modifican las automatizaciones de vigilancia.
